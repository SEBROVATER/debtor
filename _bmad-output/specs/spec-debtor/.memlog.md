- (direction) Express distillation selected because the authored PRD and addendum are rich, final inputs with no unresolved questions.
- (decision) The PRD is fully absorbed as the product source; its addendum, normative specs/design.md, and project-context.md remain adopted companions because downstream needs their line-item technical contract.
- (decision) Why: realize a dependable, deliberately small self-operated multi-currency shared-expense ledger for one administrator without collaboration or deployment complexity.
- (capability) CAP-1 intent: The administrator can sign in with one configured password, maintain an active session, and sign out while all ledger access and mutations remain protected. Success: Anonymous access is denied, valid login enables ledger use, logout and restart invalidate sessions, and unsafe requests without valid CSRF and single-use submission protection cause no mutation.
- (capability) CAP-2 intent: The administrator can create, edit, archive, restore, and when history permits delete Groups. Success: New Groups default to USD and open in Manage, archived Groups remain readable but immutable, and only Groups without Spendings can be deleted with unreferenced Participants.
- (capability) CAP-3 intent: The administrator can manage Group-owned Participant accounting identities without creating application users. Success: Participants belong to exactly one Group, referenced identities survive archival, restoration is unconditional, and archival commits only from an unchanged all-time Historical context with exact zero Group Currency Balance.
- (capability) CAP-4 intent: The administrator can record and correct a dated Spending in its Source Currency with one Payer and Proportional or Exact Shares. Success: Accepted Spendings satisfy all field, ownership, lifecycle, currency-precision, positivity, and upper-bound rules, with Payer and Shares each conserving the Total exactly and failed submissions retaining input with inline errors.
- (capability) CAP-5 intent: The administrator can browse, inspect, edit, and delete Spendings while preserving referenced history. Success: History is newest-first in fixed 25-item pages, details remain readable for archived identities using current names, direct item actions load complete aggregates, and every change commits atomically or not at all.
- (capability) CAP-6 intent: The administrator can review the selected Group's current UTC month Total and each Payer's paid Total by original Source Currency. Success: Only current-month Spendings contribute, totals remain exact, and the summary remains available without exchange-rate conversion.
- (capability) CAP-7 intent: The administrator can review the same current-month Group and per-Payer totals converted to Group Currency using date-appropriate rates. Success: Final Payer totals quantize together exactly and sum to the Group total; stale or provisional evidence is disclosed; any missing quote or checked calculation failure withholds the entire converted section while source totals and CRUD remain usable.
- (capability) CAP-8 intent: The administrator can calculate all-time Participant Balances in historical or current conversion mode. Success: Historical mode defaults to each Spending date, current mode uses the calculation date, results are deterministic and exact-zero-sum, disclosures identify context and rates, and any failure returns no partial Balances or Transfers.
- (capability) CAP-9 intent: The administrator can receive advisory Settlement Transfers that settle all-time Balances without recording repayment state. Success: Transfers are positive, deterministic, pair-unique, complete, and at most n-1 for n included Participants, without claiming global count minimality.
- (constraint) Debtor is permanently single-Administrator; Participants are Group-owned accounting identities, never users, memberships, tenants, or reusable global identities.
- (constraint) All money and rates use exact Decimal, canonical SQLite TEXT persistence, currency minor-unit validation, checked Rust arithmetic, and Rust aggregation; floating point, SQL monetary parsing/conversion/aggregation, silent rounding, zero substitution, and partial financial results are forbidden.
- (constraint) Referenced history must survive archival; destructive participant deletion is unavailable, referenced Group deletion is restricted, complete Spending writes are atomic, and calculations read internally consistent snapshots.
- (constraint) Preserve inward dependencies root to web/infra to application to domain: domain owns pure deterministic rules, application owns use cases and ports, infrastructure owns external adapters, web owns HTTP, and root only composes and manages process lifecycle; outer-library types cannot cross inward ports.
- (constraint) The one Group-centered web experience uses semantic server-rendered Askama HTML, vanilla CSS, and native links/forms; only pinned self-hosted HTMX progressive enhancement is allowed, with no custom application JavaScript, and usability/accessibility must hold across current major browsers down to 320 CSS pixels.
- (constraint) Every unsafe route requires applicable authentication, session-backed CSRF, and a bounded expiring single-use submission token reserved immediately before dispatch; secrets and sensitive ledger/provider diagnostics never enter logs or user-facing errors.
- (constraint) Production supports one Debtor process and one private local WAL SQLite volume behind a sanitizing HTTPS reverse proxy; provider availability cannot gate startup, readiness, or ledger CRUD, and all admissions, waits, caches, sessions, provider calls, and shutdown phases follow the adopted bounded-operation contract.
- (constraint) specs/design.md is normative and must be updated before behavior changes; PRD, addendum, project context, ADRs, README/config, migrations, tests, and SQLx metadata must be synchronized rather than silently interpreted through conflicts.
- (decision) Non-goal: no multi-user collaboration, Participant accounts/authentication, invitations, registration, usernames, tenants, or cross-Group Participant reuse.
- (decision) Non-goal: no repayment records, paid or settled state, settlement checkpoints/date ranges, payment initiation, or globally minimal transfer count.
- (decision) Non-goal: no arbitrary-timeframe analytics in v1, search, exports, receipt capture, recurring Spendings, bank integrations, manual rate refresh, or sessions surviving process restart.
- (decision) Non-goal: no multiple Payers, direct percentage or itemized Share modes, native applications, separate desktop UX, custom application JavaScript, multiple application instances, external database writers, or broad deployment-topology flexibility.
